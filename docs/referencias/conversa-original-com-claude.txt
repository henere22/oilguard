1. Primeiro, alinhe a interface com a mecatrônica

Antes de programar qualquer coisa, você precisa saber exatamente como os dados chegam na rede. Pergunte pra equipe:

Qual protocolo eles usam para enviar os dados (o mais comum em IoT é MQTT; às vezes é HTTP/REST simples)
Qual formato dos dados (JSON, provavelmente) — nível, temperatura, timestamp, ID do tanque
Se existe um broker/servidor já definido (ex: um broker MQTT tipo Mosquitto, ou vai direto pra um backend)
Frequência de envio dos dados

Isso é o contrato entre a parte deles e a sua — sem isso definido, você fica travado.

2. Arquitetura que você precisa construir

Olhando o protótipo que vocês já desenharam, o fluxo é: sensor → unidade IoT → nuvem (seu backend) → app/dashboard. Sua parte tem 3 blocos:

Backend/API: recebe os dados da rede, salva num banco, processa alertas (nível crítico, baixo etc.) e expõe uma API para o app consumir
Banco de dados: histórico de leituras, tanques, alertas
Frontend: o app mobile (dashboard, gráfico, alertas, histórico) e/ou o dashboard web que aparece no mockup

3. Stack sugerida pra quem está começando (sem exagerar)

Backend: Node.js + Express (ou Python + FastAPI, se preferir — ambos têm boa documentação em PT)
Banco: PostgreSQL ou até SQLite pro protótipo
Ingestão MQTT: biblioteca tipo mqtt.js (Node) ou paho-mqtt
Frontend web: React (o dashboard web do mockup dá pra fazer bem com isso)
App mobile: se quiser rodar em celular também, React Native ou até um app web responsivo primeiro, pra não duplicar esforço

4. Ordem prática de execução

Simule os dados antes de ter o sensor real (um script que manda JSON fake pro seu backend) — assim você desenvolve sem depender da mecatrônica estar pronta
Construa o backend: rota que recebe dados, salva no banco
Construa a API que devolve os dados formatados (nível atual, histórico, alertas)
Construa o dashboard web primeiro (mais rápido que app mobile)
Depois replica pro app mobile, se der tempo
Só no final, conecta com os dados reais da mecatrônica

5. O que estudar, na ordem

Fundamentos de API REST (se ainda não tem firme)
MQTT (é rápido de aprender, tem tutoriais curtos)
React básico (componentes, estado, requisições fetch)
Modelagem de banco simples (tabelas de tanque, leitura, alerta)

1. Protocolos possíveis entre o CLP e o ESP32

A resposta depende de qual CLP vocês vão usar (marca e modelo), porque ele define quais portas e protocolos existem. As opções mais comuns são estas.

Modbus RTU sobre RS-485 (serial)

É o mais comum e o mais provável. Quase todo CLP tem uma porta serial que fala Modbus.
O ESP32 não tem RS-485 nativo. Ele precisa de um módulo conversor barato (tipo MAX485).
O CLP expõe os dados em “registradores” (por exemplo, o registrador 100 guarda o nível do tanque 1), e o ESP32 lê esses números.

Modbus TCP (Ethernet)

É o mesmo Modbus, mas sobre rede. Só funciona se o CLP tiver porta Ethernet.
Aqui o roteador ajuda: o CLP entra por cabo, o ESP32 por Wi-Fi, e os dois se enxergam pelo IP.
Não precisa de conversor extra.

Sinais diretos (entradas/saídas)

Saída analógica do CLP (4-20 mA ou 0-10 V) ligada a uma entrada analógica do ESP32. Isso exige um circuito de adaptação de sinal.
Saídas digitais, que só avisam “nível baixo” ou “nível crítico”.
Funciona com qualquer CLP, mas é a opção mais limitada: transmite um valor ou um estado, não uma estrutura de dados.

Protocolos de fabricante, como Siemens S7, EtherNet/IP (Allen-Bradley) e OPC UA.

Dependem de marca e modelo, e são mais pesados de implementar no ESP32.
Eu evitaria, a menos que o CLP só ofereça isso.

Minha leitura: Modbus RTU ou Modbus TCP é o caminho mais provável, e o ESP32 tem bibliotecas prontas para os dois. Isso é assunto da mecatrônica, mas vale você perguntar pra equipe: “Qual o modelo do CLP e qual porta de comunicação ele tem?”. Sua parte continua igual, porque o ESP32 traduz tudo isso para HTTP + JSON.

2. “Simples” vs “sofisticado” na previsão

Falei isso porque o documento fala em “prever quando o óleo limpo vai acabar ou o sujo vai transbordar”, mas não diz como.

Previsão simples (extrapolação de tendência):

Você pega as leituras recentes e calcula a taxa de consumo.
Depois estima o tempo restante até o limite.
Exemplo: o tanque está em 60%, caiu 10 pontos nas últimas 2 horas (5%/hora) e o limite crítico é 15%. Então (60 − 15) ÷ 5 = 9 horas até o nível crítico.
É matemática básica, não precisa de muito dado histórico, e dá pra implementar e explicar em poucos dias.

Previsão sofisticada (modelos estatísticos ou machine learning):

Considera que o consumo varia: turnos de trabalho, dia da semana, picos e paradas.
Filtra ruído do sensor e aprende padrões, usando técnicas como séries temporais ou redes neurais.
Precisa de bastante histórico real pra treinar e validar. Ruído e “sensor ruim” também precisam ser tratados.

Por que isso importa pro seu caso: os dados da primeira fase são simulados. Um modelo sofisticado treinado em dado simulado só aprende a regra que você mesmo escreveu no simulador, então não prova nada. Por isso eu começaria pela versão simples. Se sobrar tempo e houver dado real, evolui depois. A pergunta pro professor é: “A previsão precisa ser um modelo de machine learning, ou uma estimativa por tendência atende?”

3. Escolha do roteador

Os critérios que eu usaria, em ordem de importância:

Precisa ter Wi-Fi 2,4 GHz. O ESP32 comum não conecta em 5 GHz. Isso elimina roteadores só 5 GHz.
Quantidade de portas LAN, que depende da decisão do item 1:
Se o CLP usar Modbus TCP, ele precisa de cabo. Então você quer pelo menos 2 portas.
Se tudo for por Wi-Fi, uma porta basta.
Funcionar sem internet. A rede é isolada, então ele só precisa criar a rede e distribuir IPs.
Reserva de IP (DHCP reservation). Serve para o notebook com o backend ter sempre o mesmo IP, senão o ESP32 perde o endereço do servidor.
Alimentação. Se o local tiver tomada, qualquer um serve. Se não, um que funcione por USB com power bank ajuda.

Não precisa de Wi-Fi 6/7, nem de velocidade alta. Os dados são JSONs minúsculos.
